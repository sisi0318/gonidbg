# 纯 Go 解释器的性能上限

这份笔记记录"能不能把 `interp` 优化到 dynarmic 的水平"这个问题的测量结果和结论,免得下次再从头推一遍。所有数字都在 Intel Core Ultra 9 275HX 上测的,负载是一个真实的生产混淆 `.so` 的一次签名调用(约 290 万条指令,复用同一个模拟器)。

## 现状

| 引擎 | 单次签名 | 每条指令 |
|---|---|---|
| dynarmic(JIT,静态链接 C++) | 2.1 ms | 0.72 ns |
| **interp(纯 Go)** | **9.6 ms** | **3.3 ns** |
| Unicorn(解释器,cgo) | 13.1 ms | 4.5 ns |

差距是 **4.6 倍**。

## 时间花在哪:不是指令本身,是分派

`go test -run X -bench . ./internal/arm64`

- `BenchmarkDispatchFloor`(全是 NOP,只走分派)= **1.46 ns/条**
- `BenchmarkMixed`(按真实负载配比的指令混合)= 2.3 ns/条

也就是说**约 63% 的时间是分派开销,只有约 0.85 ns 是真正干活**。这个比例决定了一切:哪怕把分派降到零,线程式解释器也只能到 ~0.85 ns/条 —— 恰好就是 dynarmic 的 0.72 ns 附近。换句话说**指令实现本身已经不是瓶颈,没有继续优化的空间**。

分派开销里真正的大头是**间接跳转预测失败**。`BenchmarkPredictability` 把这个单独量出来了:同样的指令混合、同样的内存占用,只改执行顺序 ——

- 4 条指令的重复循环(分支预测器能完全学会):**2.26 ns/条**
- 顺序杂乱(真实代码的样子):**9.3 ns/条**

**4 倍差距**。真实负载的 3.3 ns 落在两者之间,因为真实代码有循环、有重复,预测命中率介于两者之间。

顺带排除掉的两个嫌疑:

- **解码缓存的内存占用不是问题。** `BenchmarkFootprint` 显示到 8 MB 解码数据都只慢 ~8%,只有到 32 MB 才跳到 3.19 ns。真实负载是 122k 个不同地址 × 32 字节 ≈ 3.9 MB,惩罚约 5%。
- **复制分派点没用。** 经典技巧是让每个 handler 自带一个间接跳转(C 里的 computed goto),给预测器独立的历史。Go 没有 computed goto 也不保证尾调用,能做的近似是按 K 展开出 K 个分派点。实测(`scratch/dispatch`)1/2/4/8 个分派点:7.25 / 7.14 / 7.06 / 7.43 ns —— 基本持平。现代 Intel 预测器本来就用了足够长的历史,再分站点没有增量。

## 方案一:指令融合(superinstruction)

把相邻两条指令合成一个 handler,一次分派干两条的活。这是在 Go 里唯一能真正减少间接跳转数量的办法。

**融合能带来多少**(`scratch/dispatch`,BenchmarkFusionCoverage,乱序执行):

| 被融合的指令占比 | ns/条 | 相对提升 |
|---|---|---|
| 0% | 7.03 | — |
| 20% | 6.69 | 5% |
| 40% | 5.84 | 17% |
| 60% | 5.06 | 28% |
| 80% | 4.18 | 40% |
| 100% | 3.15 | 55% |

基本是线性的,符合"少一次分派就少一次预测失败"的模型。

**但真实负载的配对分布太平了。** 用 `go run -tags census ./scratch/paircensus` 统计那次签名调用的动态相邻 handler 对:

- 93.5% 的指令是紧跟前一条执行的(融合有足够的素材)
- 只有 157 种不同的 handler
- 但有 **2739 种不同的 handler 配对**,最高频的一对只占 2.81%,**前 24 对加起来才 39.6%**

而且这 39.6% 里的配对是互相重叠的(第 i 条可能既是 (i-1,i) 的后半又是 (i,i+1) 的前半),贪心选不重叠的大概只能落实六七成。所以:

- 手写 **24 个**融合 handler → 实际融合约 25-28% → **快约 8-11%**
- 手写 **60-100 个** → 实际融合约 40% → **快约 17%**
- 要到 80% 覆盖需要几百个 handler,也只有 40%,离 4.6 倍差得远

**结论:融合救不了,性价比也差。** 而且它和现有语义冲突:融合后第二条指令的 PC 不再成为"当前 PC",逐指令 hook / tracer / 调试器断点会被跳过;`StartCount(1)` 这种精确单步也会多跑一条(差分测试正好依赖它)。要做就必须在装了 code hook 或限制了指令数时关掉融合,并在装 hook 时清解码缓存。

## 方案二:真的生成机器码

唯一能追上 dynarmic 的路。关键问题是**纯 Go(CGO_ENABLED=0,没有 C 工具链)到底能不能安全地执行运行时生成的代码** —— `scratch/jitspike` 已经验证可以:

- 用 `VirtualAlloc`(Windows)/ `mmap`(Unix)拿可执行内存,走 `syscall` 不走 cgo
- 用一个 Go 汇编 stub(`.s` 文件由 Go 汇编器编译,不需要 C 编译器)跳进去
- 实测 4 个 goroutine 跑 80 万次调用 + 强制 GC,没有任何损坏
- **进入生成代码的开销 1.38 ns/次**。真实负载平均每 15 条指令才有一次非顺序跳转,所以按基本块编译的话这部分摊到每条指令只有约 0.09 ns,可以忽略

两个必须守住的约束:生成的代码不能动 **R14**(Go 的当前 goroutine 指针)和 **X15**(Go 的零寄存器);并且异步抢占信号落在未知 PC 上时 Go 不会抢占(`findfunc` 查不到就跳过),所以是安全的。

**预期收益**:

- 简单版(guest 寄存器留在内存里,每条 guest 指令发射 3-4 条 x86,块内无分支)→ 约 1.2-1.5 ns/条 → **3.5-4.3 ms**
- 块内做 guest→host 寄存器分配 → 约 0.8-1.0 ns/条 → **2.5-3 ms,基本追平**

**代价**:要写一个 x86-64 发射器 + 一套 AArch64→x86-64 翻译(基本等于把现在的解释器再写一遍)、基本块发现与链接、自修改代码时的失效、访存快路径必须内联发射(回调进 Go 太贵)、hook/trace/调试时退回解释器、SIMD/FP 的长尾。而且**只覆盖 amd64(arm64 要另写一套)**,等于放弃"任何 Go 目标平台都能跑"这个最大卖点,工程量和风险都是现在这个引擎的量级。

## 建议

**不建议为了追 dynarmic 去做 JIT。** 三个引擎的定位应该是分开的:

- 要**极限速度** → 用 dynarmic(2.1 ms,已经能用了)
- 要**零依赖、随处可编、可移植** → 用 interp(9.6 ms,比 Unicorn 还快 27%,冷启动快 13 倍,逐指令 trace 快 16 倍)
- 要**久经验证的参考实现** → 用 Unicorn

如果哪天确实需要纯 Go 的高性能,路线是明确的:JIT 可行(spike 已证),先做简单版拿到 3.5-4.3 ms,再按需加寄存器分配。但那是一个独立项目,不是对现有解释器的优化。

至于**现有解释器还能抠的**:已经做完了该做的(热路径访存特化、代码页缓存、分派批处理、32 字节解码指令、hook 按页匹配),把真实负载从 12.9 ms 降到 9.6 ms。剩下的 63% 是分派,而分派的大头是预测失败,在 Go 里没有进一步的手段。
